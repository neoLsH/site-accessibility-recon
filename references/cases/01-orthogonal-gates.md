# 案例：两道正交闸门

> 已脱敏：不保留站点标识、域名、厂商产品名与 Cookie 名。

## 现象

一个 100% SSR 的移动端 SEO 页（列表型页面，约 1.2MB，纯 HTTP 即可拿到完整数据）。但通过服务端渲染集群访问时，稳定返回一个非标准风控状态码 + 极短纯文本拒绝页。

## 第一版误判

当时只测了 `curl` 与 `curl_cffi`（两者 TLS 栈恰好都能过），观察到“带桌面 Chrome UA 被拦、带移动 Safari UA 放行”，于是结论是：**这是纯 UA 字符串规则，与 TLS、IP、headless 无关，用 HTTP 抓取即可**。这个结论是错的，并且已经把错误方案写进了代码。

## 决定性实验

后来用 Node 的 TLS 栈重测，翻出第二道闸。同一出口 IP，做 UA × TLS 的交叉矩阵：

| TLS 栈 \ UA | 桌面 Chrome | 移动 Safari |
|---|---|---|
| Chrome 指纹 | 拦 | **过** |
| Safari 指纹 | 拦 | 过 |
| Node undici（OpenSSL） | 拦 | **拦** |
| 真实浏览器（BoringSSL） | 拦 | 过 |

- 拦 Chrome UA、放行 Safari UA → 闸① = UA 字符串规则。
- 拦通用 OpenSSL 客户端（Node / Python），放行浏览器级与部分系统级 TLS 栈 → 闸② = ClientHello 指纹。
- 两闸**正交**：任一不过都返回同一个风控响应。

另一个关键对照：用 `curl` 完整复刻 Node 的 header 集与顺序 + Safari UA，仍然正常放行。证明差异在 TLS 指纹，不在 header。

## 结论

- 落地必须是**浏览器模式 + 固定移动 Safari UA**（浏览器内核的 TLS 栈过闸②，Safari UA 过闸①）。
- 走 Node `fetch` 的 HTTP 抓取路径**恒定失败**，UA 再正确也救不回。
- 该站的判定与 IP 信誉无关（同一 IP 只改 UA 或 TLS 栈即翻转）。

## 可迁移规律

1. **“内容 SSR” 不等于 “HTTP 抓取可行”**。前者说明不需要 JS 水合，后者取决于你的运行时 TLS 栈是否被放行。
2. **必须用生产真实使用的客户端栈做实验**。用两个恰好都能过的客户端测，会得到“该因素无关”的结论。
3. **正交闸门会让单变量实验看起来“没有效果”**。看到“改了 A 没变化”，先问“是不是还有 B 堵着”。
4. 同一产品线不同子域的策略可能相反，站点级配置要锁到 host，不要按域名后缀一刀切。
