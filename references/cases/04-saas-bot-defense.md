# 案例：SaaS 风控的“两道门”

> 已脱敏：不保留站点标识、域名、厂商产品名与 Cookie 名。这是“干净 IP 必要但非充分”的标准样本。

## 现象

目标页在真实浏览器里正常。自动化访问得到三种不同结果，很容易被误判成同一件事：

| 方式 | 出口 | 结果 |
|---|---|---|
| `curl`（无 JS） | 任意 | 403 |
| headless 浏览器 | 机房 IP | 200，但**空壳**（没有正文） |
| Playwright | 干净 IP | 302 到验证码页（`webdriver=true`） |
| 真实浏览器 | 干净 IP | 正常 |

## 分诊

四种结果分别落在三态：

- `curl` 403：可能是硬拦截，也可能是“缺 JS 执行”导致的边缘拒绝。需要和浏览器路径对照才能定性。
- headless 200 空壳：**态 B**，不是态 C。200 不代表通过。
- Playwright 302 验证码：**态 B**，且带明确的方向信息（IP 已干净，剩下的问题在自动化指纹）。
- 真实浏览器正常：证明内容存在、且该出口本身可用。

## 结论：两道门

1. **门① 出口信誉**：脏 IP 连挑战都不会发，直接拒绝或返回空壳。
2. **门② 自动化指纹**：干净 IP 下，`webdriver=true`、CDP 痕迹等仍会触发挑战。

两门都要过。只换 IP 不修指纹 → 继续吃验证码；只修指纹不换 IP → 继续空壳。

拦截页本身携带厂商特征（响应头、内联脚本里的厂商配置、厂商 cookie），足以**识别风控产品与模式**，但不应该去逆向它的 cookie 生成逻辑：那是黑盒、会变、且投入产出比极差。

## 可迁移规律

1. **先识别厂商与模式**，再决定策略。不同产品（CDN 层挑战、SaaS 反爬、自研网关）的判定维度不同。
2. **“200 但空壳”是独立的一档**，不要与“被 4xx 拒绝”混在一起统计。
3. **出口与指纹是正交的两道门**，做交叉矩阵（干净/脏 IP × 自动化/真实指纹）才能定量。
4. **不要逆向厂商 cookie。** 正确杠杆是出口质量 + 自动化痕迹，必要时走合规渠道。
5. 这类站点通常是**概率门**，同一条件跨次结果会翻转，单次样本不能定论。

## 置信度

mechanism（四态对照确证两道门）；良率随时点与出口变化，不作为稳定指标引用。
