# 从档案到执行

诊断的终点不是报告，是一份执行侧能照做的计划。档案写**结论与约束**，计划写**下一步动作**；
两者都要求可回归，不许手工跳步。

## 生成计划

```bash
scripts/recon.py plan recon/<代号>/profile.yaml          # 人读
scripts/recon.py plan recon/<代号>/profile.yaml --json   # 机器读
```

`plan` 做两件事：

1. **lint**——结构、证据绑定、`null` 与 `0` 混用、疑似站点常量、档案过期。
2. **推导**——按**最早失败**的闸门映射到对策等级，给出逐步动作、验证判据与停止条件。

它不联网、不改档案，也不替你做决定。`plan.level` 与推导不一致时只告警——但告警本身
通常意味着档案写的方案比问题贵。

## lint 的分级

| 级别 | 含义 | 例子 |
|---|---|---|
| ERROR | 档案不可被下游信任，先修 | `status: pass` 却没有证据；比率不在 0..1；完整率分母大于可访问样本；疑似 Cookie 名/值 |
| WARN | 可以继续，但结论有盲区 | 没测基线；没有 `content_selector`；`last_verified` 超过 30 天；闸门正交性未知 |

ERROR 不进执行。WARN 要带进报告的「未解问题」，不能当没看见。

## 层 → 级

| 最早失败的门 | 起手级 | 动作 | 为什么不是别的 |
|---|---|---|---|
| L1 链路 | — | 修 DNS / 代理 / TLS 连通 | 链路不通时谈指纹无意义 |
| L2 传输 | S2 | 换客户端栈 | 同 UA 换栈翻转，说明判的是握手 |
| L3 请求语义 | S1 | Header 自洽、导航改 XHR | 比换内核便宜 |
| L4 运行时 | S3 | 先删自己的 CDP 痕迹 | 多数“headless 被识别”是自己留的 tell |
| L4.5 行为 | S6 | 行为模型 | 只在已有行为证据时用；脆弱、收益递减 |
| L5 业务 | S7 | 合法凭证 | 先试 S0 换数据源；不绕鉴权 |
| L6 服务端策略 | 按维度 | egress→S4 / runtime→S3 / client_stack→S2 | 决策模型是组合，先找可单变量的一维 |
| L7 观测 | — | 补样本、报区间 | 样本不足时任何对策都无法验证 |

**从低层起手。** 低层失败会让高层结论全部失效；低级方案通常也更便宜。

## 五步执行

`plan` 固定输出这五步，顺序不能换：

1. **复现对照**——`matrix` 固定其它维度，先拿到基线。对照组也失败，就停在 L1。
2. **概率门定性**——`canary` 同栈多 pass。翻转率 > 0 时，后续 A/B 必须按区间比较。
3. **单变量**——只改起手级对应的那一维，其余闸门保持原样。正交性未知时尤其如此。
4. **回归**——所有 `status: pass` 的门重跑一遍；任一翻 `fail` 即回滚。
5. **回写**——更新 `gates`、`metrics.after`、`last_verified`，再 `report` 生成报告。

第 2 步容易被跳过。没有它，一次“改后成功”可能只是概率门翻到了正面。

## 失败回流

执行失败时，先分类再改方案：

| 观察 | 归到哪层 | 改什么 |
|---|---|---|
| 连接失败、DNS、代理错误 | L1 | 出口与链路，不加指纹 |
| 同 UA 换栈仍拦截 | 不是 L2 | 看 L3 请求语义与 L5 凭证 |
| 换栈后放行但内容仍空 | 抽取或 L4 | 先排除解析丢失，再看渲染 |
| 真浏览器能过、自动化不过 | L4 | 审计自己的运行时痕迹 |
| 越测越差、静置恢复 | 出口限频 | 降并发、换出口；别继续加伪装 |
| 同一 URL 跨 pass 翻转 | 概率门 | 报区间；对策按翻转率验证 |
| 干净出口 + 真浏览器仍硬阻断 | 服务端策略 | 换数据源或明确不支持 |

## 降级链与停手

每份计划都应写明「首选 → 备选 → 放弃」：

- **首选**：最低成本且证据支持的 S 级。
- **备选**：首选回归失败时的下一级；同样要写代价与影响面。
- **放弃**：出现 [countermeasure-ladder.md](countermeasure-ladder.md) 的停手条件时，
  把「当前不可解」写进 `known_issues`，不要无限试错。

停手是成本判断，不是失败。没有写进档案的「不可解」，下一个人会重新踩一遍。

## 回归与版本

- 档案每次修改都 bump `last_verified`；超过 30 天视为待复验。
- 站点级配置优先于全局默认；全局改动必须评估对全部档案的影响面。
- 回归只看判据，不看感觉：`status` 翻转、内容区跌破 `min_content_len`、
  翻转率显著上升，三者任一触发即复验。
- 报告由 `report.py` 从档案生成，不要手写——两份数据必然漂移。

## 执行红线

执行侧不得为了“过”而越过诊断边界：

- 不绕过付费墙、登录鉴权、访问控制；凭证只走合法授权。
- 不提供验证码求解、账号池、凭证填充。
- 不把站点内部常量（site id、hash、签名密钥）写进档案、配置或日志。
- 不为了单站收益做全局指纹改动；全局改动要有评审与回归。
- 探测保持节流：`canary` 上限 10 pass、默认间隔不低于 2s；连续探测会把限频
  误判成指纹识别。
