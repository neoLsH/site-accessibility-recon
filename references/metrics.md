# 双指标：可访问性成功率与内容完整率

## 为什么必须拆成两个

一次请求可能有四种结局，把它们塞进一个“成功率”里，得到的是无法行动的数字：

```
请求 ──┬─ 链路失败        （没到源站）
       ├─ 反爬拦截        （到了，被挡）
       ├─ 内容不存在      （到了，没有）
       └─ 拿到内容 ──┬─ 完整
                     └─ 不完整（空壳 / 导航 / 广告 / 登录引导）
```

前三种根因完全不同；最后一种“可访问但不完整”与前三种的对策也不重叠。

## 定义

```
可访问性成功率 = 拿到目标真实内容的请求数 / 总请求数

内容完整率   = 内容完整未降级的请求数 / 拿到内容的请求数
```

- 分母不同：内容完整率的分母是可访问成功的**子集**。
- 两个指标都必须**按路由拆分**。同一站点，列表页与详情页可能有数量级的差异。
- 链路失败、内容不存在要单列，不能混进“拦截”。

## 结算工具

```bash
scripts/recon.py stats recon/<代号>/evidence.jsonl          # 人读表格
scripts/recon.py stats recon/<代号>/evidence.jsonl --json   # 机器读
```

输入是证据行（JSONL）：

```json
{"route": "/article/1", "outcome": "ok", "content_len": 812}
```

`outcome` 取 `ok | degraded | blocked | auth | missing | noise`；也可以直接喂
`canary --save` 的 JSON。输出按路由与 `ALL` 两级给出两个比率和 Wilson 95% 区间，
噪声从可访问性分母剔除并单列。

手算最容易犯两个错：把 `degraded` 算进完整、把 5xx 算进可访问性分母；前者高估完整率，
后者把基础设施问题读成反爬。工具只做结算，不替你判断样本是否代表全量。

## 改前改后怎么比

```bash
scripts/recon.py stats recon/<代号>/evidence-before.jsonl \
  --compare recon/<代号>/evidence-after.jsonl
```

改前作位置参数、改后作 `--compare`。只看两边都有的路由，按 `after − before` 出差值，
并给 Newcombe hybrid score 95% 区间（两个独立比例的差）。判定取**未取整**的区间：

| 状态 | 条件 | 该怎么写 |
|---|---|---|
| `improved` | 下界 > 0 | “改善，区间下界 x” |
| `regressed` | 上界 < 0 | “回归”，退出码 1，先回滚再谈归因 |
| `inconclusive` | 跨 0 | “未见显著变化”，不写提升 |
| `insufficient` | 任一侧分母 < `--min-den`（默认 10）或为 0 | 补样本，不判方向 |

三个容易踩的坑：

- **点估计不算改善。** 0.750 → 0.885 看着涨了 13.5 个百分点，但区间跨 0 时只能写“未见显著变化”。
- **分母太小不出方向。** 10 条样本的区间宽到能覆盖任何结论；`insufficient` 是保护，不是失败。
- **只比同一路由。** 只在一侧出现的路由单独列出；把新增路由算进整体差值，等于用覆盖面冒充提升。

整体与按路由各有判定，整体改善不能掩盖某个路由的回归：`regressed_routes` 非空同样退出 1。

## 归因分类

| 分类 | 判据 |
|---|---|
| 链路失败 | 最终 URL 是错误页 / 代理未生效 / 连接失败 |
| 硬拦截 | 4xx 风控码、挑战页、验证码、跳风控路径 |
| 降级软拦截 | 200 + 元信息齐全 + 内容区为空或只剩导航 |
| 登录墙 | 跳登录 / 注册路径，或渲染登录引导 |
| 内容不存在 | 业务码表明删除 / 审核 / 权限 / 地域 |
| 基础设施噪声 | 5xx / 超时 / 连接重置 |

## 完整率怎么量

**必须量内容区，不要量整页。**

- 整页可见文本长度会被导航、页脚、推荐流、登录引导撑大。实测中，一个“正文被抽空、只留导航壳”的页面，整页可见文本可达 6000+ 字符，比真正的短文还长。任何整页阈值都无法同时放过短文、拦住空壳。
- 正解：为站点定义**正文选择器**（内容容器），量该容器的可见文本长度；容器缺失或长度趋零即判降级。
- 正文选择器要正则地绑定到路由（例如仅详情页路径生效），避免误伤其他页面。

**基线怎么定**：用真实浏览器打开同类页面，取内容区长度的分布（不要取最小值），得到该路由的正常量级。阈值应显著高于“导航壳 + 广告卡”的量级。

## 虚高审计

“可用”的判定几乎总会虚高，必须定期抽样人工核验。

常见虚高来源：

| 来源 | 机制 |
|---|---|
| 登录墙变丰满 | 预热后登录引导渲染出更多文案，被内容评估器判为“有内容” |
| 导航壳被当成内容 | 抽取器把导航/页脚提出来当正文 |
| 广告填充 | 内容容器残留广告卡，长度超阈值 |
| 报告截断 | 测试报告只存预览字段，用预览长度算完整率必然失真 |

审计方法：

1. 从“判为可用”的样本里分层抽样（按路由）。
2. 人工/真实浏览器核对：目标实体是否存在、正文是否达到同级量级。
3. 记录“虚高差值”。实测中曾出现原始指标 44%、真实 21% 的 2 倍虚高。
4. 把审计结论写进档案，后续引用指标时必须同时给出修正口径。

## 报告规范

- 按 **站点 × 路由 × 环境（生产/预发）× 时间** 出趋势。
- 改前改后用**同一批 URL**，否则不可比。
- 每次报数附：样本量、pass 次数、区间、噪声比例、虚高修正值。
- 不引用单 pass 点估计；不把 502 计为“被反爬”。

## 回归

方案上线后要能回答三个问题：

1. 可访问性成功率变化多少（同批 URL，前后对比）？
2. 内容完整率变化多少（不能只看“拿到 200”）？
3. 引入的代价是什么（延迟、出口消耗、误判导致的额外重试）？

对策的净收益 = 指标提升 − 代价。只报提升不报代价，等于没做评估。
