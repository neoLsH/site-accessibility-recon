# WAF 拦截的归类与处理

遇到拦截，先回答「它看的是什么」，再选处理路径。**按机制归类，不按品牌归类**：同一个品牌在不同站点可能配出完全不同的策略，而同一类机制的处理路径是稳定的。

厂商识别交给专门工具（见文末）；本 skill 只负责把现象映射到机制，因为**处理路径取决于机制**。

## 六类拦截

| 类 | 可观测判据 | 它在看什么 | 层 | 合规处理路径 | 不要做 |
|---|---|---|---|---|---|
| 1 边缘硬阻断 | 403 / 406 / 451 + 极小 body（常 < 1KB）+ 页面无站点自有静态资源；同源静态资源同样被拦 | 出口 IP / ASN / 地理 / 已知爬虫名单 | L1–L2 | 先确认是否有授权；有授权则走公司合规出口或官方 API（S0/S4） | 换 IP 池硬顶、伪造 Referer 骗过名单 |
| 2 协议栈白名单 | 同 UA 换 TLS/H2 栈结果翻转；换 UA 不翻转 | ClientHello、H2 SETTINGS、扩展顺序 | L2 | 用浏览器级协议栈（`curl_cffi`）或真实内核（S2/S5） | 只改 UA 就宣布“已解决” |
| 3 JS 挑战 / 计算型 | 首次 200 或 503，body 含挑战脚本，下发短命 cookie，无正文；带该 cookie 重放可过 | 浏览器能否执行挑战、挑战结果是否有效 | L4–L5 | 用真实浏览器内核执行（S5）；或用官方接口 | 自己复算挑战、伪造挑战 cookie |
| 4 交互验证 | 出现滑块 / 点选 / 图形码 / “请完成验证” | 人类交互证据 | L5 | 停：走官方 API、授权账号，或降低频率后重测 | 打码平台、验证码求解、账号池 |
| 5 无感评分 / 降级 | 状态 200，但内容区为空或明显缩水；跨 pass 翻转；换栈或换出口后变化 | 指纹自洽度、运行时痕迹、行为、历史信誉的综合分 | L6 | 修运行时卫生与自洽（S3）、节流、A/B 验证后再下结论 | 把降级页当成功计入指标（虚高） |
| 6 速率与配额 | 429 / 503 + `Retry-After`；连打 N 发后整体变差，静置恢复 | 请求频率、并发、配额 | L1/L6 | 遵守 `Retry-After`、退避、申请配额、加缓存（S4） | 并发硬冲、把限速误判成指纹问题 |

## 判别顺序

1. **先排除非 WAF 情况**：链路失败（DNS/TLS/超时）与内容业务状态（真 404、审核下架）不属于本表，见 [triage-and-gates.md](triage-and-gates.md)。
2. **再定第一扇过不去的门**：用 [client-matrix.sh](../scripts/client-matrix.sh) 跑同 UA 多栈、同栈多 UA，看是否翻转。
3. **单次观测不定类**：至少 3 次 pass，并保留真实浏览器对照。概率门会让一次命中看起来像“已解决”。
4. **归到类后只改一个变量**：按 S 阶梯从便宜到贵，别一次把栈、出口、内核全换掉——那样即使过了也不知道是哪一项起的作用。

## 取内容：由低到高的客户端阶梯

`scripts/fetch-page.py` 把阶梯固化下来，逐级尝试，记录每级结果：

```
native HTTP（curl） → 浏览器级协议栈（curl_cffi） → 真实浏览器内核（你自己的渲染服务）
```

- 每级都记录 `http / bytes / 内容区 / final_url`，成功即停。
- 全部失败时给出机制归类与证据，而不是“失败了”。
- 默认执行 robots 检查；`--i-have-permission` 仅用于已获站点方许可的场景。
- **不含**验证码求解、出口轮换、挑战 token 伪造。遇到第 3/4 类，脚本会明确建议改用真实内核或官方接口。

```bash
# 取一页，自动走阶梯
scripts/fetch-page.py 'https://example.com/article/1' --selector '#content'

# 批量 + 落盘 HTML + JSON 证据
scripts/fetch-page.py --from urls.txt --selector '#content' --out-dir recon/raw --json
```

## 工具（按用途，不按“能不能过”）

| 用途 | 工具 | 说明 |
|---|---|---|
| 识别/佐证厂商 | `wafw00f`、`WhatWaf` | 只在你**有明确授权**的目标上用：它们会发送攻击类载荷，属于主动扫描 |
| 协议层对照 | `curl_cffi` | 只解决 TLS/H2 层；JS 层无能为力，别指望它过挑战页 |
| 真实内核 | Playwright / Selenium / 你自己的渲染服务 | 能执行挑战，但会被运行时痕迹检测，先做 [fingerprint-methods.md](fingerprint-methods.md) 的自洽与 CDP 审计 |
| 看自己发了什么 | mitmproxy / DevTools | 确认请求头、cookie 注入顺序、重定向链 |
| 网络指纹读数 | `scripts/fp-echo.py`（tls 回显） | 只反映你这一侧，不反映目标站判定 |

## 边界

- 归类是诊断动作，不是绕过动作。本文不给“怎么过”的操作细节。
- 第 4 类（交互验证）到此为止：不求解、不代打、不用账号池。它是上游做得不够好的症状。
- 不伪造挑战结果、不篡改风控 cookie、不为规避封禁而轮换出口。
- 任何“换出口/换内核”的动作，先确认它在你的授权范围与站点条款内。
